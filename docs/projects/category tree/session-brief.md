# Category Tree — Routed Light, Block 1

## Context

The graphite Tree and new monumental trunk are the accepted baseline.

Do not resume Gate 2 and do not plant the Tree in the gravity well yet.

The Transducer concept is unchanged. This block tests one small part of it:
whether dynamic information flow can provide the perceptual connectivity that
physical surface continuity could not.

## Question

> Can one luminous information event travel continuously from one terminal,
> through its real authored parent route, into and down the trunk, making the
> hierarchy perceptually continuous despite the separate branch meshes?

Implement one routed-light study only.

## Behaviour

Choose one representative terminal with a useful multi-generation route to the
trunk.

The event must:

- follow the actual authored hierarchy and existing branch curves;
- travel terminal-to-parent towards the trunk;
- cross visible branch junctions without an apparent jump;
- enter the monumental trunk and continue downward;
- have unmistakable direction when observed over time.

The route must come from hierarchy data, not from proximity or a visually
invented path.

## Visual language

The graphite Tree remains predominantly dark.

The information should appear **inside or contained by the conduit**, not like a
spotlight projected onto its surface and not like a glowing bead pasted on top.

Use a restrained moving luminous region/trail if useful so the passing event
briefly reveals the local structure.

After it passes, the Tree should return towards graphite darkness.

Do not illuminate the whole route permanently.

Do not create disco lighting, travelling surface bands, barber poles or a
general pulsing material.

At any frozen frame the light may be ambiguous. Over time its route and
direction must be unmistakable.

## Protected baseline

Do not redesign the Tree, trunk, hierarchy, growth system, materials or crown.

Do not implement:

- multiple packets;
- aggregation;
- branch-wide luminosity;
- techno-runes;
- lava/matter flow;
- Cosmos or gravity-well integration;
- new geometry continuity work.

## Working boundary

Inspect the existing route/geometry data and implement **one approach**.

Small corrections are permitted. Do not pursue multiple rendering architectures
or recursively investigate new problems.

Judge the result in the existing Structure, Silhouette and Canopy views.

## Record and stop

Create:

`docs/projects/category tree/routed-light-investigation.md`

Record briefly:

- chosen terminal and route;
- rendering approach;
- files changed;
- technical verification;
- visual strengths and defects;
- verdict: **CONTINUE / REVISE / ABANDON**;
- one recommended next block.

A successful build is not sufficient. The experiment succeeds only if the moving
light makes the route feel continuous and internally generated rather than
decoratively illuminated.

Then **STOP and return control for visual review.**

# Category Tree — Routed Light, Block 2

Proceed from `routed-light-investigation.md`.

The Block 1 verdict **REVISE** is accepted.

## Task

Keep the existing authored routing, cumulative route distance, single-packet
clock, graphite Tree, monumental trunk and crown unchanged.

Replace only the camera-dependent surface containment with the proposed
route-local internal-core approach.

The luminous event must appear spatially contained within the branch conduits
and trunk rather than projected onto their surfaces.

It must remain continuously visible as the Tree is orbited through the existing
Structure, Silhouette and Canopy views.

Do not illuminate the complete conduit.

## Controls

Add two experimental controls:

- **Packet speed** — controls the terminal-to-root travel speed.
- **Start tier** — selects the trunk-release growth tier from which the packet
  originates.

For Start tier, deterministically choose one useful terminal belonging to the
selected tier and derive its complete route by walking the authored hierarchy.

Do not add arbitrary node selection.

Changing Start tier must visibly change the length/origin of the journey while
preserving terminal-to-root routing.

## Boundary

Implement one internal-core approach only.

Do not add multiple packets, aggregation, runes, lava, Cosmos integration,
whole-branch illumination, new geometry continuity work or unrelated controls.

If the internal-core approach requires a material redesign of the accepted
graphite Tree, stop and report that problem rather than expanding scope.

## Review

Update:

`docs/projects/category tree/routed-light-investigation.md`

Record the Block 2 implementation and judge specifically:

- visibility while orbiting;
- branch-to-trunk continuity;
- whether the event reads as internal rather than surface-projected;
- behaviour across packet speeds;
- behaviour from different start tiers;
- whether the Tree returns to graphite darkness after passage.

Give **CONTINUE / REVISE / ABANDON**, recommend one next block, then **STOP**.

# Category Tree — Routed Light, Block 3

The Block 2 **CONTINUE** verdict is accepted.

## Question

Can distributed information events throughout the manifested canopy make the
Tree read as one active information-gathering hierarchy?

## Task

Extend the accepted route-local core mechanism from one packet to multiple
independently emitted packets.

Eligible manifested terminal nodes throughout all active growth tiers may emit
information events.

Every event must:

- originate at a real manifested terminal;
- follow only its authored parent route;
- travel terminal-to-root;
- converge naturally onto shared hierarchy routes;
- enter and descend the existing monumental trunk;
- disappear completely after its wake passes.

Do not implement semantic aggregation yet. Multiple packets may independently
share the same parent route.

## Control

Replace the artistic **Start tier** control with:

**Packet frequency**

This controls overall emission density across the manifested canopy.

Do not synchronise all terminals to one clock. Give eligible terminals
deterministic distributed phases so increasing frequency produces progressively
richer traffic rather than simultaneous flashes.

Retain Packet speed.

The result must remain inspectable at the minimum and maximum frequency.

## Visual constraint

The Tree remains predominantly graphite.

At low frequency, individual terminal-to-root journeys should be easy to follow.

At higher frequency, the viewer should perceive information being gathered from
across the canopy and converging towards the trunk without the Tree becoming
uniformly illuminated.

Avoid:

- synchronised flashing;
- permanent branch illumination;
- whole-crown pulsing;
- decorative random sparkles;
- bloom used to manufacture coherence.

The light represents information traffic, not atmosphere.

## Boundary

Preserve the accepted Tree, trunk, hierarchy, growth and internal-core rendering.

Do not fix the known trunk camera-facing projection limitation in this block.

Do not add aggregation, runes, lava, Cosmos, gravity-well integration or new
geometry work.

Implement this one traffic experiment, visually inspect it, update
`routed-light-investigation.md` with strengths, defects and
**CONTINUE / REVISE / ABANDON**, recommend one next block, then **STOP**.
